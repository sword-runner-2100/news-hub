# 面向 Hy4 的优化评审｜每日新闻汇总台（news-hub）

> 评审日期：2026-11-11（北京时间）
> 评审对象：`news-hub-cloud/`（`index.html` + `scripts/*.py` + `.github/workflows/refresh.yml`）
> 线上产物：https://sword-runner-2100.github.io/news-hub/
> **性质：只评估，不改实现。** 本报告未修改任何 `index.html`、脚本、工作流或线上数据。
> 结论口径：代码事实来自本地只读检索（行号以 2026-11-11 版本为准）；Hy4 能力来自公开披露，**口径不一致处已单独标注**，不作为硬参数采用。

---

## 0. 一句话结论

这套工作台的**运行时不需要 Hy4，也不应该引入 Hy4**：它是零密钥、零成本、幂等的 GitHub Actions 流水线，一旦把付费 LLM 塞进去，会同时破坏「不依赖电脑开机」「免费」「稳定」三个核心属性。

Hy4 真正该接手的是两类**会话侧 / 离线**工作：

1. **内容质量判定**（相关性实体校验、译后校验、争议去重复核、每日摘要的严谨性）——这是当前最影响体验、又最贴合 Hy4 低幻觉 + 长文理解 + 结构化输出能力的部分；
2. **代码重构**（约 700 行纯前端逻辑 + 约 3600 行 Python 的重复逻辑收敛）——Hy4 官方明确针对「前端复杂交互、状态管理、前后端联动」做过优化。

而最需要**针对 Hy4 提前调整**的，是「把 11021 行里 86.7% 的内联数据从上下文里剥出去」，以及「把已修好的历史缺陷写成不可回退的基线」——否则 Hy4 越能干，越容易在重构时把用户已有的使用习惯改掉。

### 1.2 运行链路（workflow 10 步）

```
cron 0 1,13 UTC（北京 09:00 / 21:00）+ workflow_dispatch
 1 checkout@v7.0.1        2 setup-python 3.12      3 pip install（不钉版本）
 4 fetch_news.py ─┐  27 路并发(8线程) → 免费 gtx/MyMemory 机翻 → update_news.py
 5 fetch_linkedin.py ┐ continue-on-error:true，LI_AT cookie，SDUI/RSC 解析
 6 fetch_steam.py ─┐   SteamCharts 非公开端点
 7 fetch_youtube.py ┐  YouTube Data API + 字幕三级降级，YOUTUBE_API_KEY
 8 git commit + push（仅 index.html）
 9 push_wechat.py（仅早 9 点场次，WECHAT_WEBHOOK）
10 输出摘要（always）
```

- 三个 `update_*.py` 由对应 fetch 脚本用 `subprocess` 串联，workflow 不直接调用。
- 仅 LinkedIn 步骤允许失败；新闻 / Steam / YouTube 失败会中断整体（job 上限 15 分钟）。
- **全链路零 LLM 调用**：翻译是免费机翻端点，摘要是 RSS 片段 / 字幕抽句，分类是关键词首命中，情绪与主题是词典统计，热评是 API 原始评论排序。
- `inbox/added.json` 每次 `update_news.py` 调用都全量覆盖（步骤 4 写、步骤 5 可能再覆盖），步骤 9 读最后一份。

### 1.4 Hy4 能力对照（公开披露，含口径警示）

| 能力 | 公开披露 | 对本项目的意义 |
|---|---|---|
| 上下文 | 「突破 100 万 Token」，模型广场标 Hy4 preview 最大输入 960K / 输出 64K | 项目单次输入只有几千 Token，**超长上下文不产生额外价值**，不是选型加分项 |

| 幻觉 | **口径冲突**：见下方警示 | 与「禁止编造」红线直接相关，必须自测 |

> **口径警示（重要）**：不同来源给出的幻觉数字互不一致——「15.76% → 5.45%」（ADP 接入文）、「12.95% → 7.2%，猜测致错率 23.1% → 5.6%」（实测文）、「官方自建搜索测试猜测错误率 23.1% → 5.6%」（选型文）。评测集与统计口径未统一，且多为官方 / 内部评测。混元团队自己也明确表示「与顶尖闭源模型仍存在较大差距」。**这些数字只能作为初筛，不能写进验收指标**；本报告的验证框架（第 6 节）改用本项目自有样本盲测。
>
> 另：混元模型广场另有 **Hy-MT2 翻译专用模型**（30B/7B/1.8B，最大输入/输出均 4K），若只做翻译，它是比通用 Hy4 更对口的方向，但 4K 窗口需分块。

## 2. 四维现状梳理

### 2.1 功能组织

- **16 个模块集中在单文件**：顶栏/同步状态、视图切换、更多菜单、话题筛选（侧栏 + 底部 Tab 两套 UI）、全文搜索、近 7 日柱状图、数据操作、新闻时间线、YouTube 视频速览、Steam 双面板、图表 tooltip、导入导出、数据层、工具函数、全量编排。
- **数据与逻辑混在同一文件**：三个标记块把 86.7% 的篇幅变成数据；`DATA_VERSION` 被放在 `SEED_DATA` 标记块末尾（5703），语义上属于版本信息却绑在数据块里。
- **两套筛选 UI 由同一函数耦合**：`renderFilters`（10402–10417）在渲染侧栏的同时直接 toggle 底部 tabbar，点击时又同时调 `renderFilters()` + `renderTimeline()`（10879）。
- **话题是枚举常量而非配置**：`TOPICS` 只有 ubisoft / temu（10321–10324），CSS 另有 `.t-ubisoft/.t-temu`、`.b-*` 硬编码类名（255–266），`renderChart` 只统计这两个话题（10424–10425）。
- **README 目录结构已过期**：只列了 7 个脚本，缺 `fetch_linkedin.py` / `fetch_youtube.py` / `update_youtube.py` / `push_wechat.py` / `dedupe_lib.py`；流程图（8–15）漏掉 LinkedIn、YouTube、微信推送三步。

### 2.2 交互与展示

- **无状态层**：10839–10885 一个全局 click 委托里，每个分支直接改 `STATE` / `FILTER` 再直接调某个 `render*`，没有统一状态入口或订阅。
- **改一条就全量重绘**：`renderAll()`（10827）固定串 6 个渲染函数，7 个调用点（含已读、星标、导入、清空）。每次等价于重建 449 张新闻卡 + 78 张视频卡 + 2 个 Steam 面板 + 2 张 SVG + 1 张柱状图；YouTube 的局部操作也重绘全部 78 张卡。无分页、无虚拟滚动、无 `requestIdleCallback`，唯一惰性机制是缩略图 `loading="lazy"`。
- **状态持久化不完整的三处**：`FILTER` / `QUERY` 只在内存，刷新即重置（10368–10369）；`writeJSON` 返回布尔但 6+ 个调用点全部忽略，localStorage 配额或隐私模式失败时静默；导入（10969–10992）忽略 `version` / `ytRead` / `ytFold` / `noReseed`，且无 schema 校验。
- **转义覆盖不全**：`esc()` 全文调用 33 次，但 `updatedAt`（10565、10697）、`themes.count`（10619）、`sentiment` 数值（10643–10644）、Steam `data-p/data-a/data-n`（10751–10754）直接拼进 `innerHTML`；YouTube 缩略图还带内联 `onerror="this.remove()"`（10653）。
- **双端逻辑分叉**：768 阈值在 head 预判（16）与 `effectiveView`（10904）两处硬编码；`data-view` 在 3 处写入但 CSS 无对应选择器，实际布局只由 `.is-mobile` 决定（残留状态）。CSS 里 `is-mobile` 出现 47 次、3 组 `@media`（1180 / 900 / 769）。
- **历史缺陷刚修好、极易回退**：`loadItems()` 的「同版本也按 id 补齐 + `noReseed` 例外」（10332–10356，含 10359 的初始化顺序注释）、官方蓝色徽章 `officialBadge()`（10496–10504）、官方帖免标题去重（`update_news.py:185-188`）。这三者是上一轮「页面上看不到 LinkedIn 帖」的根因修复。

### 2.3 运行表现

- **无 SLA 依赖偏多**：Google News RSS、Bing News RSS、Google gtx 翻译端点（未文档化）、MyMemory、SteamCharts 非公开端点、5 个 Invidious 公共镜像、yt-dlp、LinkedIn 带 cookie 的 SDUI/RSC 内部树。仅 YouTube Data API v3 是官方有配额的接口。
- **零重试**：全仓库无 retry 循环，只有降级链（gtx → MyMemory；字幕 transcript-api → 5 镜像 → yt-dlp；Bing 直链失败回退原链接）。无 429 处理、无跨运行缓存、无 HTTP 条件请求；超时值散落写死 8/15/20/25/30/60 秒，并发固定 8 + 6 线程。
- **幂等语义不一致**：`update_steam.py` / `update_youtube.py` 无变化不写，但 `update_news.py:234-239` 即使 `added == 0` 也备份 + 重写 + 递增 `DATA_VERSION`，与 README:157「数据没变化就不改动文件」不符。日志是纯 print，无时间戳、无耗时、无结构化字段。
- **已知内容质量问题（用户最在意）**：
  - `guess_cat()`（fetch_news.py:279-285）关键词首命中即归类，无内容级实体校验；`reports/2026-11-11` 里 Temu 两条都不是 Temu 公司新闻（「Temu 垃圾」是形容词、David Jones 报道完全无 Temu），报告自己加了如实转述备注。
  - YouTube 仅靠 `"temu" in (title+descr)` 过滤（fetch_youtube.py:720），memory 记录需人工剔除印尼语 `temu kangen`（重逢）、泰语山寨梗等词形巧合。
  - 去重阈值 0.45 的 2-gram overlap 在 0.46 附近有误合并风险（`dedupe_lib.py:29-31` 自述）；10-28 报告仍出现「两条为同一事件的不同媒体表述」。
  - 翻译由免费机翻端点承担，README:286 承认「偶尔生硬或轻微误译」；10-27 memory 记录「2 亿美元（ € ）」与「2 亿欧元」口径不一致。
- **LLM 产物与云端刷新冲突**：11 条 `aiSummary` 由仓库外自动化写入 `index.html`，`update_youtube.py:191-195` 只特判 `summarySource=="transcript"`、无 `"ai"` 分支，云端每次刷新会把它降回 description；memory 记录这类「Actions 降级」重复 20+ 次，靠人工从 `inbox/youtube-*.json` 整条恢复。README:102「总结不靠 AI 编造」与页面实际数据不一致。

### 2.4 可维护性

- **重复逻辑**：标记块「找 START/END → 正则抽 → 字符串拼接替换」在 **7 处**各自实现（4 个 update/dedupe 脚本 + backfill + push_wechat + workflow 内联）；`balanced_object()` / `eval_js_object()` / `_quote_keys()` 在 `update_steam.py` 与 `update_youtube.py` 几乎逐行重复；`backup()` 3 份、`die()` 3 份、`log()` 5 份、`title_key()` 2 份；翻译两套（`translate_one` 双端点+缓存 vs `translate_any` 单端点 sl=auto）。
- **配置与常量散落**：27 路查询词表、38 垃圾词、10 来源黑名单、67 家 TRUSTED（`dedupe_news.py` 另有一份 **50 家且内容不一致**）、5 类分类词、38 品牌、25 术语正则（README 写 16 条）、190 条 YouTube 情绪/主题词典、5 个 Invidious 镜像、2 个 AppID、UA 字符串 5 份——全在 .py 顶部，无配置文件。
- **文档漂移**：`MAX_VIDEOS=96` vs README「上限 36 条」；README 术语「16 条」vs 代码 25 条；`fetch_news.py:41` 的 `GITHUB_TOKEN` 文档字符串是已废弃 GitHub Models 方案残留；`fetch_news.py:512` 注释写「34 路」而实际 27 路。
- **密钥面**：3 个 Secrets（LI_AT / YOUTUBE_API_KEY / WECHAT_WEBHOOK）；工作区 `.env.local` 有明文 YouTube key（已被 gitignore）。

## 3. 面向 Hy4 的适配性判定

### 3.1 三种解读，本报告采用哪一种

| 解读 | 含义 | 判定 |
|---|---|---|
| A 运行时接入 | 在 GitHub Actions 里调 Hy4 做翻译 / 摘要 / 分类 | **不建议**（破坏零密钥、零成本、幂等、无 SLA 依赖已够多） |
| B 会话侧优化 | 让 Hy4 读代码做重构、评审、生成基线 | **主推**（P2 + P0-1/P0-2） |
| C 离线内容加工 | Hy4 对已有产物做质量判定，结果经人工确认后入库 | **主推**（P1 + P0-3） |

Hy4 是**会话 / Agent 侧模型，不是常驻执行体**；本项目的执行体是 GitHub Actions。因此「面向 Hy4 优化」= 让项目**更容易被 Hy4 正确理解和安全修改**，以及**让 Hy4 在离线环节补上规则做不好的语义判断**，而不是把 Hy4 塞进流水线。

### 3.2 最适合交给 Hy4 的（收益高、风险低）

| 事项 | 为什么适合 Hy4 | 为什么现在规则做不好 |
|---|---|---|
| **相关性 / 实体校验** | 长文理解 + 指令遵循 + 低幻觉 + 可输出结构化 verdict | 关键词首命中无法区分「Temu 公司动态」与「把 Temu 当廉价形容词」 |
| **争议去重对复核** | 语义级「是否同一事件」判断 | 2-gram overlap 只看字面，0.46 附近会误合并 |
| **译后事实校验** | 能识别数字 / 货币 / 专名口径冲突 | 占位符补丁只能防音译，防不了「2 亿美元（ € ）」这类错 |
| **每日摘要严谨性** | 可强制「只用页面字段、答案不在材料中就明说」 | 现有自动化已靠 prompt 约束，但无校验 |
| **前端逻辑重构** | 官方针对状态管理 / 复杂交互专项优化 | 700 行纯逻辑里重复渲染、死代码、转义缺口靠人肉排查慢 |
| **重复逻辑收敛 + 基线测试** | 长程任务能力适合跨文件一致性改造 | 7 处标记块替换、两份近乎相同的解析器 |
| **截图视觉走查（一次性）** | 正式版新增视觉能力 | 双端 47 处 `.is-mobile` 规则人工走查成本高 |

### 3.3 需要针对 Hy4 调整的（不调整就会翻车）

| 事项 | 风险 |
|---|---|
| **上下文瘦身** | 11021 行里 86.7% 是数据；把整个文件丢给 Hy4，纯逻辑只占约 6.5%，容易被数据淹没、误改数据块，也浪费 token。**1M 上下文在这里不是优势** |
| **不可回退基线** | `loadItems` 补新逻辑、`noReseed`、官方徽章、官方帖免去重都是刚修好的历史缺陷；重构时 Hy4 很可能「顺手简化」掉 |
| **运行时边界声明** | 不显式声明「Hy4 不进 Actions」，Hy4 容易提出「接入 LLM 自动摘要」这类看似合理但破坏核心属性的方案 |
| **AI 产物归属** | 11 条 `aiSummary` 由外部 agent 写入但云端会覆盖；Hy4 若开始稳定产出总结，必须先定义优先级与幂等合并，否则产出反复丢失 |
| **验收口径** | 官方幻觉率数字口径冲突，不能直接写进验收；必须换成自有样本盲测 |

### 3.4 明确不适合交给 Hy4 的

- 定时抓取 / GitHub Pages 部署 / 密钥管理（执行体是 Actions，模型不能常驻）。
- 任何**要求确定性输出**的环节：去重阈值判定、`id` 生成、JSON 序列化、标记块替换、`DATA_VERSION` 递增——LLM 的不确定性会直接破坏幂等。
- 高频短翻译：免费 gtx 已够用，引入通用大模型在延迟与成本上不划算；若换翻译方向应评估 Hy-MT2（4K 窗口需分块），而非通用 Hy4。
- 把 1M 上下文当选型理由：项目单次输入只有几千 Token，官方选型建议也明确「实际输入只有几千 Token 时超长上下文不产生额外价值」。

## 4. 优化清单（按优先级）

### P0 · 必须调整（做 Hy4 优化的前置条件）

#### P0-1 建立「给 Hy4 的最小上下文包」 [必须｜针对 Hy4 调整]

- **当前不足**：`index.html` 538,937 字节 / 11021 行，内联数据占 86.7%（449 新闻 + 78 视频 + 2 游戏）；纯逻辑约 700 行。现有 README / overview 是叙述性文档，没有「模块 → 函数 → 行号 → 数据流」的结构化地图，也没有标注哪些区域不可改写。
- **优化目标**：产出一份不含数据的逻辑骨架清单（模块边界、函数索引、三个标记块的起止与语义、localStorage 契约、workflow 步骤映射），作为 Hy4 会话固定上下文；明确把三个标记块列为只读数据区。

- **影响范围**：**仅新增文档 / 生成脚本**，不改 `index.html` 数据块、不改任何 Python 脚本、不改 workflow。
- **验证要点**：① 骨架里每个行号与当前文件逐项比对一致；② 一次 Hy4 会话能正确复述 16 个模块边界与 3 个标记块位置；③ 该步骤对仓库产生 **0 个文件 diff**；④ 与 README 目录结构漂移项逐条对齐。

#### P0-2 固化「不可回退基线」与回归检查 [必须｜保护核心功能]

- **优化目标**：把核心不变量写成可执行检查清单——字段 schema、id 规则、三个标记块、`wb_newshub_*` key 与 `STATE` 五个字段、话题枚举、AppID、去重阈值 0.45、官方帖免去重、中文标题占比、双端布局契约、09:00/21:00 排期。

- **影响范围**：新增检查脚本 / 文档；**运行时代码零改动**。
- **验证要点**：① 对当前 `index.html` 跑一遍全绿；② 故意改坏一个字段（如删 `noReseed`、改阈值、破坏标记块）能准确报错；③ 手动触发 Actions 前后 diff 只允许出现在三个标记块内；④ 用一份旧的 localStorage 快照打开页面，已读 / 星标不丢、新条目能补进来、清空后不回填。

#### P0-3 明确「Hy4 不进运行时」并解决 AI 产物覆盖 [必须｜针对 Hy4 调整]

- **优化目标**：把 Hy4 定位为会话侧优化 agent + 离线内容加工；为 AI 总结定义明确优先级（ai > transcript > description）与幂等合并，产物落到独立文件再合并，不让云端脚本覆盖。

## 6. 统一验证框架（所有 P1 语义类改动共用）

参照公开选型建议并结合本项目红线，建议这样验，而不是引用任何厂商评测数字：

1. **评测集**：从真实历史数据抽 50–100 条 / 对，覆盖主力场景与边界（11-11 的 3 条弱相关新闻、`temu kangen` 类噪声、同事件不同表述、含数字货币的译文、官方帖重复）。
2. **陷阱题**：必须包含「答案不在材料中」的样本，检查是否如实回答无法确认——**这项比正确率更能反映生产可用性**。
3. **统一 prompt 基线**：同一套 prompt 跑所有候选模型 / 版本，避免调优程度不同导致结论失真；便于用户横向对比。
4. **三类指标**：效果得分（准确率 / 误杀率 / 误合并率）、P95 延迟、实际 Token 消耗（**区分输入 / 输出 / 缓存命中**）。
5. **人在回路**：P1 全部先产审阅清单，人工确认后才影响 `index.html`；任何不确定样本保留原状，不自动改写。
6. **回归门**：任何改动前后，P0-2 基线全绿 + 三个标记块逐字节比对 + Actions 手动触发 success + 双端走查 + 旧 localStorage 快照可打开。

## 7. 事实口径与不确定性说明

## 核心看点

1. **别把 Hy4 接进 Actions。** 运行时零 LLM 是这套系统的优点不是缺口；引入付费模型会同时打掉「不依赖电脑开机 / 零成本 / 幂等」。Hy4 该在会话侧和离线环节发力。
2. **最该交给 Hy4 的是「相关性判定」。** 11-11 的 3 条新增里，Temu 两条都不是公司新闻——这正是关键词规则的天花板，也是低幻觉 + 长文理解模型收益最高、风险最低的位置。
3. **做 Hy4 优化前必须先做两件事**：把 86.7% 的内联数据从上下文剥出去（P0-1），把刚修好的可见性缺陷写成不可回退基线（P0-2）。否则 Hy4 越能干，越容易改掉用户习惯。
4. **有一处真实冲突需要决策**：11 条 AI 总结由外部 agent 写入，云端每次刷新会覆盖，已重复 20+ 次。这不是模型能力问题，是产物归属与幂等合并问题（P0-3 / P1-4）。
5. **两处一致性漂移值得顺手记账**：README 与 workflow 步骤数、术语条数、视频上限均已不一致；`update_news.py` 空变化仍重写，与文档承诺的幂等相反。
6. **验收别用厂商数字。** 幻觉率公开口径至少三套且互不一致，改用自有 50–100 样本 + 「答案不在材料中」陷阱题，才符合「不编造、要交叉验证」的要求。
